# QueryRepository ログはなぜ全てを記録するのか

BEAR.QueryRepository には、異例なほど徹底したキャッシュログが同梱されています。
open/event/close のツリー、20 数個の型付きコンテキストクラス、コンテキスト
ごとに 1 つの JSON Schema、テストスイート内でのスキーマ検証、そして自身の
ログが検証を通らなければ exit 0 しないデモ群です。この文書は、その規模が
意図的である理由 — 排除するために存在する失敗のクラス、設計を形づくった
原則、そしてそれが利用者に課すコスト — を説明します。

## キャッシュは静かに壊れる

イベント駆動の無効化を持つ分散キャッシュは、見えない機械です。壊れても何も
throw しません。アプリケーションは 200 を返し続けます — 古い内容とともに。
静かな誤りはソフトウェアで最も高コストな失敗モードであり、キャッシュ無効化
はその自然な生息地です。「新鮮」と「永遠に古い」の差は、誰かが catch できる
例外ではありません。起きなかったことを誰も目撃しなかった、1 回の無効化の
不在です。

これはこのパッケージにとって仮定の話ではありません。v1.16.1 まで、2 つ以上
の子を embed する `#[Cacheable]` リソースは、最後の子を除くすべての子への
依存を静かに失っていました（`CacheDependency::depends()` が蓄積した
surrogate key を追加せずに上書きしていた）。失われた子を purge しても親は
無効化されません。古いページが、無期限に、エラーなしで、本番で。このバグは
数年間生き延びました — しかも*キャッシュログと共存して*。旧来のフラットな
ログは surrogate key を出力してさえいました。文字列の並びの中で欠けた依存
エッジを誰も見ることはできませんでした。ログには依存グラフを可視化する構造
がなく、記録を検査可能にする契約もなかったからです。

この事故が目標を定めます。**キャッシュが行うすべての決定は観測可能でなければ
ならない — 人が読め、テストが固定でき、機械が検証できる形で。**

## このログは何であるか

**ツリーはドメイン構造そのものです。** GET はスコープを開き、embed された子
の GET はその内側にネストし、スコープは hit/miss の結果とともに閉じます。
書き込みは `command` スコープを開いてメソッド、その `#[Refresh]`/`#[Purge]`
アノテーション、それらを実行したインターセプターを記録し、結果として生じた
無効化をその下にネストします — 原因と結果が 1 つの部分木に収まります。信頼
しなければならない依存グラフは、目に見える形そのものです。

**コンテキストはどれも 1 つの決定点です。** 語彙 — `cache_hit`、`cache_miss`、
`depends_on`、5 種の `save_*`、`invalidate`、`purge`、`put_skipped`、
`cache_error`、`pre_write_cleanup`、`manual_*` スコープ群 — は冗長さでは
ありません。キャッシュサブシステムが行うと決定し得るすべての列挙です。save
コンテキストが 5 つあるのは、物理的に異なる書き込み経路が 5 つあるからです。
統合すれば、デバッグの場面で必要になるまさにその区別が消えます。語彙の
大きさはドメインについての事実であり、設計の欠陥ではありません。

## 原則

**1. 沈黙する経路を作らない。** すべてのコード経路は、事実を出すか、出さな
かった理由を出します。保存は `saved` の結果を記録します — 書き込みを拒否した
プールが、成功した保存に見えることはもうありません。put が続かない miss は
理由付きの `put_skipped` を出します（`etag-present`、実際のレスポンスコードを
伴う `error-code`、`not-cacheable`）— 保存の不在は記録された決定であり、謎
ではありません。無効化はターゲットごとの結果（`roPool`/`etagPool`:
`invalidated`|`failed`、`cdn`: `purged`|`failed`|`skipped`）と所要時間を
報告します。失敗した書き込みでも command スコープは開かれ、その 4xx とともに
閉じられます — purge が*正しくスキップされた*ことを記録するのです。

**2. 事実は発生源で記録し、読み手に推論させない。** 書き手はなぜ無効化するか
を知っています。読み手が推測する必要はないはずです。`pre_write_cleanup`
マーカーが存在するのは、このパッケージが代替案を試したからです。以前の
リビジョンは cleanup と無効化の区別を読み手側のタグ相関ルールで分類しており、
判定可能にするまでに 2 周を要し、それでも判定不能なドーナッツのケースが
残りました。書き込み地点でマーカーを 1 つ記録することが、その手続き全体を
削除しました。推論ルールは腐りますが、記録された事実は腐りません。

**3.「不明」を「何も起きなかった」に見せかけない。** `cache_error` イベントは、
キャッシュ経路が失敗したことと、`exceptionClass` に何がそれを失敗させたかを
記録します — 縮退したキャッシュと冷えたキャッシュを区別し（プール障害後の
miss はエントリの不在ではない）、その両方を、保存が行う作業そのもののバグ
（描画に失敗するビューなど）から区別します。ロギングのプロトコル自体が誤用
された場合 — LIFO 違反、flush 時に閉じられていないセッション — コアのロガーは
失敗した正確な地点に `semantic_logger_error` 診断を in-band で記録し、
ツリーを保ちます。データを失い得るログは、そのことを in-band で言わなければ
なりません。

**4. ログは散文ではなく契約である。** すべてのコンテキストは `TYPE` と
`SCHEMA_URL` を持ち、すべての型は `docs/schemas/context/` に JSON Schema を
持ちます。テストスイートは出力されたツリーすべてをそれらのスキーマに対して
検証し（`SemanticLogTreeTrait`）、デモは自身の出力をオフラインで検証して
違反時には非ゼロで終了します。コードとスキーマは、ビルドを落とさずに乖離
することができません。これは通常の劣化を反転させます。普通のログは振る舞いが
変わった瞬間に嘘へと腐りますが、このログは CI が真であり続けさせる、キャッシュ
振る舞いの実行可能な仕様です。

## 誰が読むのか

**人間。** `vendor/bin/stree` はセッションをツリーとして描画します
（`php demo/run-dependency.php`）。イベントを持たない hit、
cleanup-invalidate-save の連なりを伴う miss、依存エッジ、command のカスケード。

**テスト。** ツリーの形は `SemanticLogSchemaTest` とその仲間に固定されています
— ログは回帰の防具も兼ねます。v1.16.1 のバグのクラスは、いま構造として見えます。
`save_etag` の tags が子のすべてを蓄積している親スコープは、アサーション
1 つの距離にあります。

**機械。** ここが AI 時代のために作られた部分です。キャッシュを診断する
エージェントは、文字列を grep して推測するのではありません。セッションを
flush し、すべてのノードが自身のスキーマをリンクしたツリーを得て、機械的に
推論します — miss の前にあるプールの `cache_error` は障害を意味し、冷えた
キャッシュではありません。その `exceptionClass` は、そもそもプールが失敗した
ものだったのかを告げます。`put_skipped{error-code, 404}` は、保存しなかった
ことが意図的だったことを意味します。`pre_write_cleanup` マーカーを伴わない
`invalidate` は本物のキャッシュバストです。グラウンドトゥルースと公開された
スキーマが、キャッシュのデバッグを民間伝承から検証へと変えます。エージェントが
必要とする読解ルールはパッケージに同梱されています（`docs/llms.txt`、
`docs/llms-full.txt`）。

## コスト — そしてなぜ既定でオフなのか

3 階層の embed ページ、1 回の実行あたり 2000 キャッシュヒットでの実測:

| | リクエストあたり | リクエストあたりの蓄積量（未 flush） |
|---|---|---|
| `NullSemanticLogger` | 0.018 ms | 4 B |
| `SafeSemanticLogger` | 0.023 ms | 1409 B |

問題は CPU ではありません — 5 µs はキャッシュ 1 往復のごく一部です。問題は
蓄積です。リクエストあたり 1.4 KB は、セッションがプロセスとともに死ぬ
PHP-FPM では無償ですが、決して flush しないワーカーでは無限に伸びます。

残りを決めるのはもう 1 つの実測です。4 つのデモ自身の出力を数えると、健全な
セッションには 28〜95 のうち失敗エントリが**ゼロ**しか含まれません — そして
失敗だけで構成された `run-degraded.php` でさえ、失敗 10%、足場 90% です。常に
すべてを記録することは、利益のすべてを量と引き換えにすることになります。

そこで既定は沈黙です。キャッシュエンジン（`NullAdapter`）とまったく同じように、
何も記録せず、何も蓄積せず、flush の義務も負いません。アプリケーションは、
ログが読まれる開発時にこれを有効化します:

```php
$this->install(new DevQueryRepositoryLogModule($appDir . '/var/log/query-repository', module: new QueryRepositoryModule()));
```

そして本番では、ほかの何によっても説明できないセッションだけを残します —
変更、起きなかった作用、そしてサンプル:

```php
$this->install(new ProdQueryRepositoryLogModule('php://stdout', sampleRate: 1000, module: new QueryRepositoryModule()));
```

flush はモジュールに付いてきます。ブートストラップの 1 行ではありません。
モジュールはシャットダウン時の flush を登録します。それはリクエストの終わり方
すべてを生き延びる唯一の境界です — 出力の後、304 の早期 `exit()` の後、
捕捉されなかったエラーの後。

サイドチャネルは構成上サイドチャネルのままです。koriym/semantic-logger 0.9
以降、ロガーは全域的です — 決して throw せず、プロトコルの誤用は in-band の
`semantic_logger_error` 診断として記録します — したがってロギングの失敗が
キャッシュの読み書きを壊すことはあり得ず、また隠れることもできません。ログが
半分だけ存在して誤解を与える第三の状態は存在しません。
